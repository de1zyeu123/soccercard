# 《足球命格》产品动线设计（v3 · PM 口径版）

## 0. 版本结论

本版基于 v2 做产品口径修正，重点调整 6 件事：

1. 明确「出生信息」是核心计算输入，不再把球风题当作主计算依据。
2. Phase 1 只存结果，不存原始生日、出生地等敏感输入。
3. Phase 2 队长能力需要登录/轻身份体系，管理链接只能作为兜底。
4. 拼队不做手动排阵，默认一键生成；人数超出时才需要队长选择成员。
5. 数据埋点放到下一阶段，不作为首版动线硬依赖。
6. 补充重复加入定义和默认处理策略。

本文件仍然只定义产品动线和信息架构，不包含结果命名、文案库、视觉方案和技术实现细节。

---

## 1. 产品目标

《足球命格》是一个世界杯周期的传播型 H5。

核心故事：

> 根据你的出生信息，推算你生来就是球场上的什么角色。

用户输入出生相关信息后，系统生成一个娱乐化足球身份结果，并引导用户保存图片、发给朋友、形成二次点击。

首版目标不是做严肃命理工具，而是做一个有「计算感」、有「身份感」、有「群聊传播感」的娱乐测试。

---

## 2. 分期策略

### Phase 1：单人测试 + 单人卡传播闭环

目标：

- 用户完成测试。
- 用户获得有传播价值的个人结果卡。
- 用户愿意把图和链接发到群聊、朋友圈、小红书。
- 朋友通过链接/二维码回流到朋友结果落地页，再进入自己的测试。

### Phase 2：拼队玩法

目标：

- 队长创建球队。
- 成员通过链接/二维码加入并测试。
- 系统自动生成球队合影。
- 合影继续带来群聊传播。

Phase 2 不在 Phase 1 首版内实现，但 Phase 1 需要预留结果字段和素材复用能力。

---

## 3. Phase 1 用户动线

### 3.1 总览

```text
【A 普通入口】                         【B 朋友分享入口 · 主力】
A1 强钩子页                           B1 朋友结果落地页
玩法承诺 + 示例结果                    朋友结果 + 挑衅句 + 测我的 CTA
        │                                      │
        └──────────────┬───────────────────────┘
                       ▼
              ① 出生信息输入
       性别 / 出生日期 / 出生时间 / 出生地
                       ▼
              ② 揭晓动效 1.5-2.5s
                       ▼
              ③ 个人结果页
       大结果名 / 角色图 / 金句 / 保存图片
                       ▼
              ④ 传播引导
       保存图 + 复制带回流链接的话术
                       ▼
              朋友点击链接或扫码
                       ▼
              回到 B1，形成闭环
```

### 3.2 入口 A：普通入口

适用用户：

- 直接打开链接的新用户。
- 从广告、主页、社交平台进入的用户。

首屏任务：

- 让用户立刻理解玩法。
- 让用户相信输入成本很低。
- 让用户想知道「我会是什么角色」。

页面内容：

- 主钩子句。
- 2-3 个示例结果。
- 「30 秒生成」类承诺。
- CTA：「测我的足球命格」。

### 3.3 入口 B：朋友结果落地页

适用用户：

- 点了朋友发出的链接。
- 扫了朋友分享卡上的二维码。

首屏任务：

- 先展示朋友的结果，制造围观和比较欲。
- 不展示朋友完整解读，避免用户停在围观。
- 用一句挑衅/邀约，把围观者转成测试者。

页面内容：

- 朋友结果名。
- 朋友角色图。
- 一句挑衅/邀约。
- CTA：「测我的足球命格」。

原则：

- B 线是主传播入口，应优先优化。
- B1 只负责转化，不负责解释。

## 4. 输入设计

### 4.1 输入原则

因为产品故事是「生来就是球场上的什么角色」，所以出生信息必须是主输入。

球风题可以作为补充反差题，但不应压过出生信息。否则用户会觉得这是普通性格测试，而不是「命格」。

### 4.2 字段建议

| 字段 | 建议 | 原因 |
|---|---|---|
| 性别 | 必填 | 命理计算和角色形象都需要。传统命理里性别会影响部分推算逻辑。 |
| 出生日期 | 必填 | 核心输入。承担「命格感」和主要计算锚点。 |
| 出生时间 | 必填，但提供「不知道」选项 | 八字时柱关键。用户不知道时，走降级算法，不阻断完成。 |
| 出生地 | 必填，城市快捷选择 | 用于出生地/真太阳时/地域修正口径。交互必须轻，不能手打长地址。 |
| 球风题 | 选填或轻量补充 | 用于制造「我以为 vs 系统判定」反差，不作为主计算依据。 |
| 位置题 | 不建议 Phase 1 必填 | 容易让用户提前定义自己，削弱系统判定感。 |
| 昵称 | 保存分享卡时再问，选填 | 用于卡片个性化，不应阻断结果生成。 |

### 4.3 输入完成策略

推荐首版输入：

1. 性别。
2. 出生日期。
3. 出生时间，含「不知道」。
4. 出生城市。

可选补充：

- 「你以为自己更像哪种球风？」  
  只做反差和文案素材，不做主判定。

产品口径：

> 出生信息决定你的球场命格；球风选择只是看看你自己以为你是谁。

## 5. 结果页设计

### 5.1 第一屏

第一屏只服务传播，不服务解释。

必须出现：

- 大结果名。
- 角色图。
- 金句。
- 保存图片按钮。

不建议第一屏堆太多解释字段。

### 5.2 下滑内容

可展示：

- 国家命格。
- 球员原型。
- 建议场上位置。
- 简短命理解释。
- 「为什么你是这个角色」。

建议场上位置需要结构化保存，供 Phase 2 自动生成球队图使用。

### 5.3 来源分流

同一个结果页需要根据入口上下文分流：

- 普通单人用户：保存图片后进入传播引导。
- 从球队加入链接进入的成员：生成结果后自动归入球队，再进入加入成功页。

开发实现上需要在 URL 或会话状态里携带 `teamId` / `source`。

## 6. 分享闭环

### 6.1 核心判断

保存图片本身不能形成闭环。

微信、朋友圈、小红书里的图片通常不能直接点击跳转。因此传播闭环必须依赖：

- 图片。
- 回流链接。
- 二维码或短链兜底。

### 6.2 分享动作

保存成功后，系统应同时提供：

1. 已保存的结果图。
2. 自动复制的一句话。
3. 一句话内包含回流链接。
4. 图片内包含二维码或短链。

示例结构：

```text
我是 XX 命格，系统说我天生适合踢 XX。
你也测一下：{shareUrl}
```

### 6.3 分享卡必须承担的任务

分享卡不是海报，是增长入口。

必须包含：

- 用户结果身份。
- 可被朋友理解的挑衅/邀约。
- 产品名。
- 二维码或短链。

## 7. Phase 1 数据策略

### 7.1 只存结果，不存原始输入

同意「只存 result」。

Phase 1 不应存储原始生日、出生地、出生时间等敏感输入。计算完成后，原始输入应立即丢弃或只保留不可逆摘要。

建议最小结果结构：

```text
resultId
resultType
roleAssetId
genderPresentation
countryType
playerArchetypeType
position
shareTitle
shareImageUrl
createdAt
source
teamId?   // 仅 Phase 2 场景存在
```

### 7.2 保存周期

建议设置结果有效期。

默认策略：

- 单人结果：保留 30-90 天。
- 团队结果：保留到世界杯周期结束后一定时间。

具体周期可在技术方案阶段确定。

## 8. Phase 2 身份与权限

### 8.1 关键判断

如果没有登录/身份体系，队长无法可靠保存自己的球队管理权。

单纯依赖管理链接可行，但很脆弱：

- 队长换设备会丢。
- 队长清缓存会丢。
- 管理链接转发出去会失控。
- 无法做成员管理和权限边界。

因此 Phase 2 如果要做「队长管理球队」，建议引入轻量登录或身份绑定。

### 8.2 推荐身份方案

推荐：

- 成员加入：不强制登录。
- 队长创建球队：需要登录或轻身份绑定。

可选方式：

- 微信授权。
- 手机号验证码。
- 邮箱 magic link。
- 第三方账号登录。

具体方式取决于上线渠道。

### 8.3 权限模型

| 角色 | 权限 |
|---|---|
| 队长 | 创建球队、查看成员、选择成员、生成球队图、删除异常成员 |
| 成员 | 加入球队、查看自己的结果、重新测试并替换自己的候选位 |
| 访客 | 查看公开落地页、开始测试 |

### 8.4 管理链接与口令

管理链接仍可保留，但定位应调整为兜底，而不是主身份体系。

建议：

- 队长登录后可查看管理页。
- 管理链接只作为快速回到管理页的入口。
- 管理链接不要出现在公开分享图或群聊文案里。
- 如果需要共享管理，可增加队伍口令或邀请管理员能力。

共享二维码 + 口令更适合「加入球队」，不适合作为唯一队长权限。

## 9. Phase 2 拼队玩法

### 9.1 核心原则

拼队不做手动排阵。

用户要的是快速生成可发群的球队图，不是一个复杂阵容编辑器。

### 9.2 队长动线

```text
队长完成单人测试
        ▼
点击「组一支队」
        ▼
创建球队，获得加入链接/二维码
        ▼
发到群里
        ▼
成员陆续加入并完成测试
        ▼
队长一键生成球队图
        ▼
保存并发回群
```

### 9.3 生成规则

默认规则：

- 人数未超过目标人数：一键生成，不需要队长选择。
- 人数超过目标人数：队长需要选择入图成员。
- 位置由系统自动分配。
- 阵型由系统自动选择或固定默认阵型。
- 不做手动拖拽排位。

### 9.4 人数不足场景

建议支持人数不足也能生成。

原因：

- 等凑满 11 人会降低传播速度。
- 群聊传播需要快速反馈。
- 空位可以反过来刺激拉人。

可选表达：

- 「当前 5 人小队」
- 「还差 6 人开赛」
- 空位显示「等你上场」

### 9.5 人数超出场景

当成员超过目标人数时：

- 队长选择入图成员。
- 未入选成员进入替补区。
- 系统可提供「一键推荐首发」。

不建议首版做复杂阵型编辑。

## 10. 重复加入定义与策略

### 10.1 什么是重复加入

重复加入指：

- 同一个成员多次点击同一个球队链接测试。
- 同一个成员反复生成多个结果并加入同一支球队。
- 用户刷新、回退、重复提交，导致同一个人出现在成员列表多次。

如果不处理，会导致：

- 球队成员列表变脏。
- 队长选择成本增加。
- 同一个人占多个位置。
- 合影结果不可信。

### 10.2 推荐策略

如果 Phase 2 有登录：

- 同一个 `teamId + userId` 只保留一条有效成员记录。
- 用户重新测试时，默认替换自己的旧结果。
- 页面文案写清楚：「重新测试会替换你在这支队里的结果」。

如果 Phase 2 暂无登录：

- 用 `teamId + deviceId` 做弱去重。
- 同一设备重复测试默认替换旧结果。
- 保留「为朋友代测」作为单独入口，避免误伤多人共用设备场景。

## 11. 数据埋点

数据埋点先放下一阶段，不作为当前动线文档的硬依赖。

但产品上需要预留事件位，避免后续无法补。

下一阶段建议补充：

- 入口来源。
- 开始测试。
- 完成输入。
- 看到结果。
- 保存图片。
- 复制分享话术。
- 点击回流链接。
- B1 到输入页转化。
- 点击组队。
- 创建球队。
- 成员加入。
- 生成球队图。

## 12. 风险与边界

### 12.1 命理口径

页面需要明确这是娱乐测试，不做严肃命运判断。

建议小字：

> 娱乐测试，仅供玩梗，不代表真实职业、性格或命运判断。

### 12.2 数据隐私

因为会输入出生信息，产品必须降低用户顾虑。

建议表达：

> 出生信息仅用于本次计算，不保存原始生日、出生时间和出生地。

### 12.3 权限风险

如果做队长管理：

- 队长权限必须有身份绑定。
- 管理链接不能公开出现在分享卡。
- 成员加入链接可以公开传播。

---

## 13. 当前产品决策

| 问题 | 决策 |
|---|---|
| 性别、出生地是否保留 | 保留。它们属于命理计算和故事可信度的一部分。 |
| 原始输入是否保存 | 不保存。只保存结果。 |
| Phase 2 是否需要登录 | 队长功能建议需要登录/轻身份绑定；成员加入不强制。 |
| 是否手动排阵 | 不做。系统自动生成。 |
| 人数不满能否生成 | 建议可以生成，并用空位刺激拉人。 |
| 人数超出如何处理 | 队长选择入图成员，系统自动排位。 |
| 管理链接是否可用 | 可作为兜底，不作为唯一权限体系。 |
| 重复加入如何处理 | 同一用户/设备在同队只保留最新结果。 |
| 数据埋点 | 放下一阶段，但预留事件位。 |
